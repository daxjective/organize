# organize — 파일 정리 자동화 도구 설계

- 작성일: 2026-08-19
- 상태: 검토 대기
- 대상 저장소: `Automation`

---

## 1. 배경

현재 저장소에는 사진 정리용 일회성 스크립트 11개가 루트에 평평하게 놓여 있다.
공통 모듈도, 진입점도, 설정도 없이 각 파일이 독립 실행 스크립트다.

기존 스크립트의 구조적 문제:

| 문제 | 내용 |
|---|---|
| 경로 하드코딩 | `C:\Users\notebiz765\...` — **현재 PC의 사용자명이 아니다** (실제는 `cloocus`). 그대로 실행하면 전부 실패한다. |
| 미리보기 불가 | 폴더를 순회하며 즉시 `shutil.move` / `os.remove`. 실행 전에 결과를 알 방법이 없다. |
| 되돌리기 불가 | 이동 내역을 기록하지 않는다. |
| 영구 삭제 | `os.remove`를 직접 호출한다. 복구 수단이 없다. |
| 연도 오탐 | `re.search(r'(19\|20)\d{2}', filename)` 이 파일명 아무 곳이나 매칭한다. `screenshot_1920x1080.png` → **1920년** 폴더로 간다. |
| 중복 판정 비결정적 | `os.walk` 순회 순서가 어느 파일을 남길지 결정한다. 같은 폴더를 두 번 돌려도 결과가 다를 수 있다. |
| 코드 중복 | 해시 함수가 4곳, 이동 로직이 5곳에 복사되어 있다. |

## 2. 목표

여러 정리 작업을 **골라서 순서대로 엮어 실행**하는 도구를 만든다.
자주 쓰는 조합은 이름을 붙여 저장하고 재사용한다.

### 2.1 제품 원칙

이 셋은 다른 모든 결정보다 우선한다.

1. **로컬에 실제로 있는 파일만 다룬다.** 클라우드에 있고 디스크에는 없는 파일(OneDrive 온라인 전용)은
   읽지도 옮기지도 않는다. 이 도구의 목적은 내 컴퓨터 안의 파일을 정리하는 것이지 동기화가 아니다.
2. **폴더는 그대로 둔다.** 흩어진 파일을 폴더에 담는 것이 이 도구의 일이다.
   폴더를 옮기는 것은 사용자가 그 기능을 **명시적으로 켰을 때만** 한다 (§5.5).
3. **이미 있는 폴더를 두고 같은 뜻의 폴더를 새로 만들지 않는다** (§6.7).
   폴더가 늘어나면 정리가 아니라 더 어려워진다.

### 2.2 사용 대상

**작성자 본인만이 아니라 다른 사람에게 건네줄 수 있는 도구**로 만든다. 따라서:

- 설정 파일을 손으로 열어 고치게 하지 않는다. 필요한 설정은 전부 GUI 에서 한다.
- 첫 실행에 아무것도 설정하지 않아도 동작해야 한다 (§6.4 별칭 자동 감지).
- 오류 메시지는 사람 말로 쓴다. `FileNotFoundError` 를 그대로 노출하지 않고,
  무엇이 문제고 무엇을 하면 되는지를 쓴다.
- 최종적으로 파이썬 없이 실행되는 exe 로 배포한다 (구현 마지막 단계).

명시적 비목표:

- **AI/LLM 판정을 쓰지 않는다.** 같은 입력이면 항상 같은 결과가 나와야 한다.
  미리보기에서 본 내용과 실제 실행 결과가 한 글자도 달라선 안 된다.
- 폴더 이름 변경(리네임) 기능은 넣지 않는다. Obsidian 내부 링크, 바로가기,
  git 경로가 깨지고 되돌릴 비용이 기능 가치보다 크다. 사용 빈도도 극히 낮다.

## 3. 실행 환경

### 3.1 개발 PC 는 고정이 아니다

**이 도구는 특정 PC 를 전제하지 않는다.** 현재 개발에 쓰는 PC 는 2026-08-31 이후
사용하지 않는다. 그 뒤에는 다른 PC 에서 개발과 실행이 이어진다.

이 제약은 가정이 아니라 이미 일어난 일이다. `legacy/` 의 스크립트들은
`C:\Users\notebiz765` 를 가리키고 있는데 그것은 **그 이전 PC** 다. PC 가 바뀌면서
전부 죽었고, 그것이 이 재작성의 출발점이다.

따라서 이 문서에 등장하는 구체적 경로·버전·파일 개수는 **오늘 관측한 사실이지 사양이 아니다.**
사양은 아래 최소 요구사항뿐이다.

### 3.2 최소 요구사항

| 항목 | 요구 | 이유 |
|---|---|---|
| Python | **3.11 이상** | `tomllib` 이 3.11 에 들어왔다 |
| OS | Windows 10 이상 / Linux / macOS | 경로 별칭이 OS 별로 갈린다 (§6.4) |
| tkinter | 포함되어 있을 것 | Windows·macOS 기본 포함. Linux 는 `python3-tk` 별도 설치 |
| 외부 패키지 | 없음 | §12 |

실행 전 환경을 스스로 점검하는 명령을 둔다 (§9 `organize doctor`).
새 PC 에 앉았을 때 무엇이 부족한지 사람이 찾아다니지 않아도 되게 한다.

### 3.3 현재 개발 환경 (2026-08-19 관측, 참고용)

사양이 아니라 지금 무엇을 확인했는지의 기록이다.

| 항목 | 값 |
|---|---|
| 개발 | WSL2, Python 3.12.3 |
| 실행 | Windows Python 3.14.6, tkinter 8.6 |
| 사용자 폴더 | `C:\Users\cloocus\...` (WSL 에서 `/mnt/c` 로 읽기·쓰기 가능) |

WSL 에서 코드를 쓰고 같은 파일을 Windows Python 으로 실행할 수 있었다. 파일 복사가 불필요했다.
새 PC 에서 WSL 이 없다면 Windows 에서 직접 편집·실행하면 되고, 설계는 영향받지 않는다.

`/mnt/c` 경유 파일 I/O 는 매우 느리다. 특히 해시 계산처럼 전체 바이트를 읽는 작업은
Windows 네이티브 대비 체감 수십 배 차이가 난다. **실사용 실행은 Windows Python 으로 한다.**
WSL 실행은 임시 폴더 대상 테스트 용도로만 쓴다.

### 3.4 사용자 폴더 위치는 고정이 아니다

관측 당시 이 PC 에는 같은 이름의 폴더가 두 벌 있었다.

```
C:\Users\cloocus\Desktop             6개   레지스트리상 당시 진짜 바탕화면
C:\Users\cloocus\OneDrive\바탕 화면   3개   OneDrive 백업이 켜지면 여기가 진짜가 됨

C:\Users\cloocus\Pictures            1개
C:\Users\cloocus\OneDrive\사진       4개   사진은 이미 여기가 더 많았다
```

`~/Desktop` 으로 하드코딩하면 OneDrive 백업이 켜진 PC 에서 엉뚱한 폴더를 정리한다.
따라서 사용자 폴더는 **런타임에 OS 에 물어본다** (§6.4 경로 별칭).

### 3.5 새 PC 로 옮길 때

저장소를 클론한 뒤 이 순서면 동작해야 한다. **이것이 이식성의 인수 조건이다.**

```
1. git clone
2. python -m organize doctor      환경 점검. 부족한 것을 사람 말로 알려준다
3. python -m organize gui         첫 실행 화면이 폴더 위치를 자동 감지한다
4. (필요하면) 설정 화면에서 백업 드라이브 등 사용자 별칭만 추가
```

`config.local.json` 은 `.gitignore` 되어 있으므로 새 PC 에는 없다.
**없어도 3번까지는 반드시 동작해야 한다.** 사용자 별칭을 쓰는 레시피만 4번이 필요하다.

레시피와 프로파일은 별칭만 쓰므로 저장소에 그대로 따라온다.

## 4. 핵심 설계 — 계획(Plan)과 실행(Apply)의 분리

기존 스크립트의 근본 문제는 "순회하며 곧바로 옮긴다"는 점이다.
새 구조는 이를 4단계로 분리한다.

```
[1] 스캔    폴더를 읽고 Action 목록을 만든다. 파일을 건드리지 않는다.
[2] 표시    Action 목록을 사람에게 보여준다.
[3] 실행    승인하면 목록대로 실행하고, 실행한 내역을 RunLog로 남긴다.
[4] 취소    RunLog를 역순으로 재생해 되돌린다.
```

미리보기와 실제 실행이 **같은 Action 목록**을 쓰기 때문에 결과가 반드시 일치한다.

### 4.1 Action

```python
@dataclass(frozen=True)
class Action:
    kind: Literal["mkdir", "move", "quarantine", "extract"]
    src:  Path | None      # mkdir 은 None
    dst:  Path | None      # quarantine 은 격리 경로
    reason: str            # 사람이 읽는 근거. UI에 그대로 표시된다.
    block: str             # 이 Action 을 만든 블록 이름
```

`reason` 은 장식이 아니라 필수다. "왜 이 파일이 여기로 가는가"를 사용자가
미리보기에서 즉시 이해할 수 있어야 실행 버튼을 누를 수 있다.

예:

```
move        screenshot.png  ->  02_Media/          route: 확장자 .png
quarantine  가이드 (1).pdf   ->  .organize/trash/   dedup: 내용 동일 (원본 가이드.pdf)
move        IMG_20231215.jpg -> 2023/              by_date: EXIF 촬영일 2023-12-15
```

### 4.2 Plan

```python
@dataclass
class Plan:
    actions: list[Action]
    skipped: list[tuple[Path, str]]   # (파일, 건너뛴 이유)
```

블록은 `Plan` 을 만들 뿐 파일을 만지지 않는다. 블록의 시그니처는 하나로 통일한다.

```python
def build(target: Path, config: dict, ctx: Context) -> Plan
```

블록끼리 직접 호출하지 않는다. 체인 실행은 러너가 담당한다.

### 4.3 체인 실행에서의 상태 전달

2번 블록은 1번 블록이 만들어낼 파일을 볼 수 있어야 한다
(예: `unzip` 이 푼 파일을 `dedup` 이 검사해야 한다).
하지만 미리보기 시점에는 그 파일이 아직 없다.

해결: `Context` 가 **가상 파일 시스템 뷰**를 들고 있다.

```python
class Context:
    def files(self, root: Path) -> list[Path]   # 실제 파일 + 앞 블록이 만들 파일
    def apply(self, plan: Plan) -> None         # 가상 뷰에 Plan 을 반영
```

러너는 블록마다 `build()` 호출 후 결과를 가상 뷰에 반영하고 다음 블록으로 넘긴다.
`--apply` 시에는 전체 Plan 을 모아 한 번에 실행한다.

`extract` Action 만 예외적으로 내용을 미리 알 수 없다 (zip 내부 목록은 읽을 수 있으므로
파일명·크기는 알 수 있고, 해시는 알 수 없다). 따라서 **미리보기 단계에서
`unzip` 다음의 `dedup` 은 zip 내부 파일에 대해 "실행 후 판정" 으로 표시**하고,
실제 실행 때 해시를 계산한다. 이 한계는 UI에 명시한다.

## 5. 작업 블록

블록 하나가 파일 하나다. 1차 범위는 4개.

### 5.1 `unzip` — 압축 해제

폴더 안의 `.zip` 을 지정한 폴더로 평탄화 해제한다.

기존 `zipper*.py` 대비 개선:

- **한글 파일명 복구.** 구형 Windows 알집으로 만든 zip은 파일명이 cp949로 저장되어
  있는데 파이썬은 기본적으로 cp437로 읽는다. `name.encode('cp437').decode('cp949')`
  로 복구를 시도하고, 실패하면 원본 이름을 쓴다.
- **zip-slip 방어.** 압축 내부 경로에 `../` 가 들어있으면 대상 폴더 밖으로
  파일을 쓸 수 있다. 해제 경로가 대상 폴더 안인지 반드시 검증한다.
- **원본 zip 삭제는 옵션이며 기본값은 삭제하지 않음.** 삭제 시에도 격리 폴더로 보낸다.

### 5.2 `dedup` — 중복 제거

기존 `dup2.py` 는 **모든 파일의 전체 해시**를 계산한다. 5,000개면 5,000번 전체 읽기다.
크기가 다르면 내용이 같을 수 없으므로 대부분은 해시가 불필요하다.

3단계로 거른다:

```
1) 파일 크기로 묶는다                    → 크기가 유일한 파일은 여기서 제외 (해시 0회)
2) 크기가 같은 것만 앞 8KB 해시          → 대부분 여기서 갈린다
3) 앞 8KB도 같은 것만 전체 해시          → 진짜 중복만
```

**남길 원본을 정하는 규칙을 명시한다.** 위에서부터 순서대로 적용하며, 모두 동률이면
경로 문자열 사전순으로 확정한다 (완전 결정적).

```
1) 파일명에 복사본 표식이 없는 쪽
   표식: (1) (2) ... / _1 _2 ... / " - 복사본" / " - Copy" / "_copy"
2) 경로가 더 짧은(상위 폴더에 있는) 쪽
3) 수정시각이 더 오래된 쪽
4) 경로 사전순
```

### 5.2.1 읽는 범위와 치우는 범위를 나눈다

폴더를 건드리지 않으면서도 중복 제거가 쓸모 있으려면 두 범위를 분리해야 한다.

| 범위 | 대상 | 하는 일 |
|---|---|---|
| **읽는 범위** | 대상 폴더 + 하위 폴더 전부 | 해시만 계산한다. **참고용** |
| **치우는 범위** | 대상으로 지정한 폴더의 **직속 파일만** | 격리 폴더로 옮긴다 |

즉 "이미 정리해 둔 하위 폴더에 같은 내용이 있으면, 새로 들어온 직속 파일을 치운다" 가 된다.
하위 폴더 안의 파일은 어떤 경우에도 옮기거나 지우지 않는다.

관측 사례: `Documents/PicPick` 은 루트에 150개, 사용자가 손으로 만든 `6월/` 278개,
`6월9일/` 31개를 갖고 있었다. 루트 150개를 하위 309개와 대조한 결과 겹치는 것은 0개였다
(즉 아직 정리되지 않은 파일들이었다). 대조 자체는 WSL 경유로 7.2초 걸렸다.

해시는 md5를 유지한다 (충돌 공격이 문제되는 용도가 아니고, 크기 일치까지 확인하므로
실사용에서 오탐 확률은 무시할 수 있다). 다만 3단계까지 통과한 쌍은
**최종적으로 바이트 비교를 한 번 더 한다** — 파일을 지우는 작업이므로 확실히 한다.

### 5.3 `route` — 규칙 기반 분류

파일을 보고 프로파일 규칙에 따라 카테고리 폴더로 옮긴다.
바탕화면 정리와 vault 번호 체계가 **같은 블록**이다. 프로파일만 바뀐다.

규칙은 위에서부터 검사해 **처음 맞는 것**을 쓴다. `default = true` 규칙이 마지막에 온다.

**자기 폴더 보호:** `route` 가 만든 결과 폴더(`01_Docs` 등)는 다시 스캔하지 않는다.
그렇지 않으면 재실행할 때마다 폴더가 중첩된다.

### 5.4 `by_date` — 날짜별 분류

날짜 판정 우선순위:

```
1) EXIF DateTimeOriginal        (Pillow 가 있을 때만. 없으면 조용히 건너뜀)
2) 파일명의 날짜 패턴            (아래 한정된 형태만 인정)
3) 파일 수정시각(mtime)
4) 판정 불가 → 옮기지 않고 그대로 둔다
```

**파일명 패턴을 엄격히 한정한다.** 기존 `(19|20)\d{2}` 는 오탐이 심하다.
인정하는 형태는 다음뿐이다:

```
YYYYMMDD          8자리 연속 (앞뒤가 숫자가 아닐 것)   20231215
YYYY-MM-DD        구분자 - _ . 허용                  2023-12-15, 2023_12_15
YYYY년MM월DD일
```

추출한 날짜는 **1990-01-01 ~ 오늘+1일** 범위 안에 있어야 한다.
`1920x1080` 은 8자리 연속 규칙에 걸리지 않고, 설령 걸려도 월 `20` 이 유효하지 않아 탈락한다.

4번(판정 불가)에서 파일을 `99_Unsorted` 로 보내지 않는 이유: `by_date` 는 보통
`route` 다음에 이미 분류된 폴더에 적용된다. 거기서 다시 미분류로 빼내면 앞 단계 결과를
망가뜨린다. 그냥 그 자리에 두는 편이 안전하다.

폴더명 패턴은 설정값이다: `{year}`, `{year}/{month}`, `{year}_{kind}` 등.

**자기 폴더 보호:** `route` 와 마찬가지로 `by_date` 가 만든 결과 폴더(이름이 설정된
패턴과 일치하는 폴더)는 다시 스캔하지 않는다. 그렇지 않으면 재실행할 때마다
`02_Media/2023/2023/` 처럼 중첩된다.

### 5.5 `move_folders` — 폴더 옮기기 (기본 꺼짐)

**기본값은 꺼짐이다.** 사용자가 명시적으로 켰을 때만 폴더를 옮긴다 (§2.1 원칙 2).

하위 폴더를 통째로 지정한 곳으로 옮긴다. 폴더 **안**은 절대 건드리지 않는다.

```json
{ "block": "move_folders", "dest": "00_Folders" }
```

켜기 전에 경고한다: 폴더를 옮기면 그 안을 참조하던 바로가기, 프로젝트 설정,
터미널 경로, git 원격 설정이 깨질 수 있다.

`.git`, `node_modules`, `.venv` 등 도구가 만든 폴더가 들어 있으면 기본적으로 제외하고
미리보기에 이유를 표시한다.

### 5.6 `empty_dirs` — 빈 폴더 청소

정리 후 파일이 빠져나가 비어버린 폴더를 치운다. 처음부터 비어 있던 폴더도 대상이다.
격리 폴더로 보내므로 되돌릴 수 있다.

`.git` 같은 숨김 폴더와 `.organize/` 는 제외한다.

## 6. 프로파일 — 분류 규칙은 코드가 아니라 데이터

TOML을 쓴다. 파이썬 3.11+ 의 `tomllib` 로 표준 라이브러리만으로 읽을 수 있고,
주석을 달 수 있어 손으로 편집하기 좋다.

`profiles/desktop.toml`:

```toml
name = "바탕화면·다운로드 정리"

[[rules]]
to  = "01_Docs"
ext = [".pdf", ".docx", ".xlsx", ".pptx", ".hwp", ".txt", ".md", ".html"]

[[rules]]
to  = "02_Media"
ext = [".jpg", ".jpeg", ".png", ".gif", ".mp4", ".mov", ".heic", ".webp", ".avi", ".mkv"]

[[rules]]
to  = "03_Design"
ext = [".psd", ".ai", ".fig", ".sketch", ".xd"]

[[rules]]
to  = "04_Apps"
ext = [".exe", ".msi", ".msix", ".appimage", ".dmg"]

[[rules]]
to  = "05_Archives"
ext = [".zip", ".7z", ".tar", ".rar", ".gz"]

[[rules]]
to  = "06_Code"
ext = [".py", ".js", ".ts", ".ipynb", ".json", ".sql", ".sh"]

[[rules]]
to      = "99_Unsorted"
default = true
```

### 6.1 폴더 네이밍 규칙

- 번호 접두사 `01_` 부터 순번. 미분류만 `99_` 로 고정해 항상 목록 맨 아래에 둔다.
- 이름은 짧은 영문 한 단어. 폴더 목록의 폭이 일정해 눈에 잘 들어오고,
  CLI에서 공백·한글 이스케이프가 필요 없다.
- `99_Unsorted` 는 "잡동사니 창고"가 아니라 **규칙에 구멍이 있다는 알림판**이다.
  여기 파일이 쌓이면 프로파일에 규칙을 추가해야 한다는 신호다.

### 6.2 지원하는 규칙 조건

1차 범위에서는 아래만 지원한다. 전부 결정적이다.

| 키 | 의미 |
|---|---|
| `ext` | 확장자 목록 (소문자 비교) |
| `name_contains` | 파일명에 포함된 문자열 목록 |
| `name_regex` | 파일명 정규식 |
| `older_than` | `"2y"`, `"6m"`, `"30d"` — mtime 기준 |
| `larger_than` | `"100MB"` |
| `has_exif_camera` | EXIF 에 카메라 `Make`/`Model` 이 있는지 (`true`/`false`). Pillow 필요 |
| `default` | 어느 규칙에도 안 걸렸을 때 (마지막에 하나만) |

한 규칙 안의 여러 조건은 AND로 묶인다.

`has_exif_camera` 는 **스크린샷·화면 캡처를 이름과 무관하게 가려낸다.**
카메라·스마트폰 사진에는 EXIF `Make`/`Model` 이 반드시 들어가고 화면 캡처에는 절대 없다.
파일명에 "screenshot" 이 없어도 정확히 걸린다 (관측 사례: 유튜브 캡처 105개가
`사피엔스 스튜디오 - ...[영상ID - 해상도 - 타임스탬프].png` 형태로 이름에 아무 단서가 없었다).

Pillow 가 없으면 이 조건이 붙은 규칙은 **건너뛰고** 다음 규칙으로 넘어간다.
실행이 실패하지 않으며, 건너뛴 사실을 미리보기에 표시한다.

### 6.3 목적지는 다른 위치도 될 수 있다

`to` 는 기본적으로 작업 루트 기준 상대 경로다. 별칭을 쓰면 다른 드라이브로도 보낼 수 있다.

```toml
[[rules]]
to  = "02_Media"            # 상대 → <root>/02_Media
ext = [".jpg", ".png"]

[[rules]]
to  = "@archive/사진"        # 별칭 → F:/day/사진 (드라이브를 넘어감)
ext = [".raw", ".dng"]
older_than = "1y"
```

목적지가 다른 드라이브면 `copy2` 후 검증하고 원본을 지운다.
격리 폴더는 작업 루트에 그대로 두므로 되돌리기는 정상 동작한다.

### 6.4 경로 별칭 — 이식성

레시피와 프로파일에는 **절대 경로를 적지 않는다.** 별칭만 쓴다.

```
레시피 / 프로파일    별칭만 사용 (@downloads)     git 에 올림, PC 무관
config.local.json   이 PC 에서의 실제 경로        .gitignore 로 제외, GUI 가 편집
```

#### 내장 별칭

```
@home  @desktop  @downloads  @documents  @pictures  @music  @videos
```

Windows 는 이 폴더들을 모든 PC 에 보장한다 (관측 확인: Desktop/Downloads/Documents/
Pictures/Music/Videos 전부 존재). **설정 없이 어느 PC 에서든 잡힌다.**

**런타임에 OS 에 물어본다.** 하드코딩도, 레지스트리 직접 파싱도 아니다.

| OS | 방법 |
|---|---|
| Windows | `ctypes` 로 `SHGetKnownFolderPath` 호출 — **OneDrive 리디렉션이 반영된 실제 경로**를 돌려준다 |
| Linux / macOS | XDG 사용자 디렉터리 설정 → 없으면 홈 기준 기본값 |

`ctypes` 는 표준 라이브러리이므로 의존성은 여전히 0이다.
사용하는 FOLDERID: Desktop `{B4BFCC3A-DB2C-424C-B029-7FE99A87C641}`,
Downloads `{374DE290-123F-4565-9164-39C4925E467B}`,
Documents `{FDD39AD0-238F-46AF-ADB4-6C85480369C7}`,
Pictures `{33E28130-4E1E-4676-835A-98395C3BC3BB}`.

#### 설정은 2단으로 병합된다

```
config.default.json    git 포함    모든 PC 공통 기본값
config.local.json      git 제외    이 PC 에서 덮어쓴 것만
```

`config.default.json` — 저장소에 같이 다니므로 **새 PC 에서 이것만으로 동작한다.**

```json
{
  "paths": {
    "archive": "@documents/Archive",
    "photos":  "@pictures",
    "work":    "@documents"
  }
}
```

`config.local.json` — 이 PC 에서만 덮어쓴다.

```json
{ "paths": { "archive": "F:/day" } }
```

```
이 PC    @archive -> F:/day               (local 이 덮어씀)
새 PC    @archive -> Documents/Archive     (local 이 없으니 default)
```

기본값이 전부 표준 폴더 아래를 가리키므로, 아무것도 설정하지 않은 PC 에서도
레시피가 그대로 돈다.

#### 별칭은 대체 경로를 가질 수 있다

별칭 하나에 경로를 여러 개 적으면 **위에서부터 실제로 존재하는 첫 경로**를 쓴다.

```json
{ "paths": { "archive": ["F:/day", "D:/보관", "@documents/Archive"] } }
```

```
외장하드를 꽂았을 때   -> F:/day
안 꽂았을 때           -> @documents/Archive
전부 없으면            -> 마지막 것을 만든다 (미리보기에 "폴더 생성" 으로 표시)
```

**레시피가 PC 를 옮겨도, 드라이브를 안 꽂아도 죽지 않는다.**
설정이 고정값이 아니라 우선순위 목록이라는 점이 이 도구의 이식성을 만든다.

#### 사용자 별칭

```json
// config.local.json   (.gitignore 로 제외)
{
  "paths": {
    "archive": "F:/day",
    "photos":  "D:/사진보관",
    "work":    "~/OneDrive/문서"
  }
}
```

**GUI 설정 화면에서 편집한다** (§10.3). 손으로 열 필요가 없다.

다른 PC 로 옮기면 이 파일만 다르다. 정의되지 않은 별칭을 만나면 실행을 멈추고
설정 화면을 열어 어떤 위치를 지정해야 하는지 보여준다.

#### 저장 형식 규칙

`tomllib` 은 **읽기 전용**이다. 표준 라이브러리로 TOML 을 쓸 수 없다.
따라서 형식을 용도로 가른다.

| 대상 | 형식 | 이유 |
|---|---|---|
| `profiles/*.toml` | TOML | 사람이 손으로 쓰고 프로그램은 읽기만 한다. 주석을 달 수 있다 |
| `config.default.json` | JSON | 저장소에 포함되는 공통 기본값 |
| `config.local.json` | JSON | GUI 가 쓴다 |
| `recipes/*.json` | JSON | GUI 가 쓴다 |

**읽기만 하면 TOML, 쓰기도 하면 JSON.** 이 규칙 덕분에 외부 의존성이 필요 없다.

### 6.5 Johnny.Decimal 프로파일 (향후)

확장자 기반 분류는 **파일이 무엇인가**(형식)를 보고, Johnny.Decimal은
**무엇에 관한 것인가**(주제)를 본다. 후자는 확장자로 알 수 없으므로 자동화가 불가능하다.
따라서 2단 구조로 쓴다.

```
[1단] 바탕화면·다운로드  →  확장자 자동 분류      ← 이 도구가 자동으로
[2단] 문서 보관소        →  Johnny.Decimal      ← 사람이 손으로
```

2단이 필요해지면 `profiles/vault.toml` 을 한 장 더 만들면 된다.
파이썬 코드는 손대지 않는다. **1차 범위에는 넣지 않는다.**

### 6.6 폴더명 오버라이드 (GUI 편집)

일반 사용자가 가장 많이 원하는 커스터마이즈는 "규칙을 바꾸는 것"이 아니라
**"목적지 폴더 이름을 내 식대로 바꾸는 것"** 이다 (`01_Docs` → `문서`).

프로파일 TOML 을 고쳐 쓰는 대신, **오버라이드만 따로 저장**한다.

```json
// config.local.json
{
  "paths": { ... },
  "folder_names": {
    "desktop": {
      "01_Docs":  "문서",
      "02_Media": "사진과 영상"
    }
  }
}
```

- 원본 프로파일을 건드리지 않으므로 도구를 업데이트해도 사용자 설정이 살아남는다.
- 적어놓지 않은 것은 프로파일의 기본값을 그대로 쓴다.
- TOML 쓰기가 필요 없다.

GUI 에서는 이 표만 편집한다. **확장자 목록과 조건은 읽기 전용으로 보여주기만 한다.**
상세 규칙을 바꾸려는 사용자는 `profiles/*.toml` 을 직접 편집한다 (1차 범위에서는 GUI 미지원).

### 6.7 이미 있는 폴더를 두고 또 만들지 않는다

폴더가 늘어나면 정리가 아니라 더 어려워진다. 세 단계로 막는다.

#### ① 같은 이름이 있으면 "기존 폴더 사용" 으로 표시

이미 `02_Media` 가 있으면 새로 만들지 않고 그대로 쓴다. 당연한 동작이지만
**미리보기에서 "폴더 생성" 과 "기존 폴더 사용" 을 구분해 보여준다.**
사용자가 "또 만드는 건 아닌가" 하고 불안해하지 않아야 한다.

Windows 는 대소문자를 구분하지 않으므로 `Docs` 와 `docs` 는 같은 폴더로 취급한다.

#### ② 목적이 겹치는 폴더가 있으면 매핑을 제안

스캔할 때 대상 폴더의 기존 하위 폴더 목록을 읽고, 만들려는 폴더와 뜻이 겹치는 것을 찾는다.

```
만들려는 것   02_Media
이미 있는 것  사진 · 이미지 · Pictures
제안          "02_Media 대신 '사진' 을 쓸까요?"
```

고르면 `config.local.json` 의 `folder_names` (§6.6)에 저장되어 다음부터 자동 적용된다.

판정은 **결정적**이다. AI 를 쓰지 않는다.

```
1) 이름 정규화     공백·기호 제거, 소문자, 번호 접두사(01_) 제거
2) 완전 일치 또는 포함 관계
3) 동의어 표 조회   프로파일에 데이터로 둔다
```

```toml
# profiles/desktop.toml
[synonyms]
"02_Media" = ["사진", "이미지", "그림", "Pictures", "Media", "Images", "영상", "Videos"]
"01_Docs"  = ["문서", "자료", "Documents", "Docs"]
"05_Archives" = ["압축", "Archive", "Zip"]
```

제안일 뿐이며 무시해도 된다. 무시하면 원래 이름으로 만든다.

#### ③ 날짜 체계가 이미 있으면 경고

`by_date` 가 `2026/` 을 만들려는데 대상 폴더에 이미 날짜성 폴더가 있으면 멈추고 알린다.

```
이미 있음    6월/  6월9일/
만들려는 것  2026/

경고: 이미 날짜로 나뉜 폴더가 2개 있습니다.
      연도별 분류를 켜면 날짜 체계가 두 가지로 섞입니다.
      [그래도 진행]  [이 작업 끄기]
```

날짜성 폴더 판정: 이름이 `YYYY`, `YYYY-MM`, `N월`, `N월N일`, `YYYY년` 등
날짜 패턴에 맞으면 날짜성으로 본다.

관측 사례: `Documents/PicPick` 에 사용자가 손으로 만든 `6월/`, `6월9일/` 이 있었다.
여기에 연도별 분류를 돌리면 `2026/` 이 생겨 같은 목적의 폴더가 세 종류가 된다.

## 7. 레시피 — 블록을 엮은 것

GUI에서 저장하므로 쓰기가 쉬운 JSON을 쓴다 (표준 라이브러리).

`recipes/downloads.json`:

```json
{
  "name": "다운로드 정리",
  "roots": ["@downloads"],
  "steps": [
    { "block": "unzip",   "delete_original": false },
    { "block": "dedup" },
    { "block": "route",   "profile": "desktop" },
    { "block": "by_date", "target": "02_Media", "layout": "{year}" }
  ]
}
```

### 7.1 roots 와 상대 target

레시피는 **대상 폴더 목록 `roots`** 를 별칭으로 지정하고, 각 step 의 `target` 은
각 root 기준 상대 경로다 (생략하면 root 자신).

```json
"roots": ["@downloads", "@desktop", "@documents/PicPick"]
```

**대상은 사용자가 채우는 목록이다.** 도구가 알아서 하위 폴더를 파고들지 않는다.
`Downloads/GitSSok` 을 정리하고 싶으면 `roots` 에 직접 추가한다.
이 모델 덕분에 "하위 폴더를 어디까지 처리할까" 라는 판단이 아예 필요 없다.

각 root 는 **독립적으로** 파이프라인을 돈다. 로그와 격리 폴더도 root 마다 따로 생긴다
(`<root>/.organize/`). 한 root 가 실패해도 나머지는 계속한다.

`--root @desktop` 으로 목록을 통째로 덮어쓸 수 있다.

마지막 단계가 `route` 가 만든 `02_Media` 를 다시 연도별로 쪼갠다.
확장자 분류가 시간이 지나면 비대해지는 문제를 체인으로 해결하는 부분이다.

### 7.1.1 step 공통 옵션

모든 블록이 아래 세 옵션을 똑같이 받는다.

| 옵션 | 뜻 | 생략하면 |
|---|---|---|
| `target` | **어디서 찾을지** (root 기준 상대) | root |
| `dest` | **어디로 보낼지** (별칭 사용 가능) | `target` — 즉 제자리 정리 |
| `when` | **어떤 파일만** (§7.3) | 전부 |

`dest` 가 있으면 결과를 다른 위치로 보낸다.

```json
{ "block": "by_date",
  "when":   { "ext": [".md"] },
  "dest":   "@documents/메모",
  "layout": "{year}" }
```

```
@desktop/2026-07-12 회의록.md  ->  @documents/메모/2026/2026-07-12 회의록.md
```

`dest` 가 작업 루트 밖이면 §8.1 의 크로스 루트 규칙을 따른다 (로그에 원래 경로가 남아
되돌리기는 정상 동작).

### 7.1.2 블록 하나만 쓰기

step 이 1개인 레시피는 **예전의 단일 목적 스크립트와 같다.**
체인은 "엮을 수 있다"는 뜻이지 "엮어야 한다"가 아니다.

| `legacy/` 의 스크립트 | 대응하는 step |
|---|---|
| `sort.py` (연도별) | `by_date` 1개 |
| `dup2.py` (중복 제거) | `dedup` 1개 |
| `zipper.py` (압축 해제) | `unzip` 1개 |
| `202604_update.py` (종류+연도) | `route` → `by_date` 2개 |

달라지는 것은 미리보기·되돌리기가 생기고 경로가 하드코딩되지 않는다는 점뿐이다.
GUI 에서는 체크박스 하나만 켜면 단일 블록 실행이 된다.

### 7.2 파일 형태별 분기 — 방식 A: 폴더가 곧 분기

`route` 가 먼저 파일을 갈라놓으면, 다음 블록은 **폴더만 지정하면 자동으로 그 종류만** 처리한다.
별도 분기 문법이 필요 없다.

```json
"steps": [
  { "block": "route",   "profile": "desktop" },

  { "block": "dedup",   "target": "02_Media" },
  { "block": "by_date", "target": "02_Media", "layout": "{year}" },

  { "block": "by_date", "target": "01_Docs",  "layout": "{year}" }
]
```

```
route 실행 후
  01_Docs/    문서만    -> 연도별로만
  02_Media/   사진만    -> 중복제거 + 연도별
  04_Apps/    설치파일  -> 아무 처리 안 함
```

### 7.3 파일 형태별 분기 — 방식 B: `when` 필터

`route` 를 거치지 않고 특정 파일만 골라 처리하려면 step 에 `when` 을 붙인다.
**모든 블록에 공통으로 적용**된다.

```json
{ "block": "by_date", "when": { "ext": [".jpg", ".png", ".heic"] } },
{ "block": "dedup",   "when": { "larger_than": "10MB" } },
{ "block": "route",   "when": { "older_than": "2y" }, "profile": "cold-archive" }
```

`when` 의 문법은 **프로파일 규칙(§6.2)과 완전히 동일하다.**
`ext`, `name_contains`, `name_regex`, `older_than`, `larger_than` 을 그대로 쓰고,
여러 조건은 AND 로 묶인다. 매칭 코드가 재사용되고 사용자가 새로 배울 문법도 없다.

구현상으로도 러너가 블록에 파일 목록을 넘기기 전에 걸러주기만 하면 되므로,
**블록 코드는 바뀌지 않는다.**

### 7.4 두 방식을 합친 예

```json
{
  "name": "종합 정리",
  "roots": ["@downloads", "@desktop"],
  "steps": [
    { "block": "unzip" },
    { "block": "dedup",   "when": { "larger_than": "1MB" } },
    { "block": "route",   "profile": "desktop" },

    { "block": "by_date", "target": "02_Media", "layout": "{year}/{month}" },
    { "block": "by_date", "target": "01_Docs",  "layout": "{year}",
      "when": { "older_than": "1y" } },
    { "block": "route",   "target": "02_Media", "profile": "cold-archive",
      "when": { "older_than": "3y" } }
  ]
}
```

마지막 step 이 "3년 넘은 사진은 `@archive` 드라이브로 보낸다" 에 해당한다
(`cold-archive` 프로파일의 `to` 가 `@archive/...` 를 가리킨다).

### 7.5 넣지 않는 것

if/else 중첩, 서브 파이프라인, 반복문 같은 본격 분기 트리는 넣지 않는다.
폴더 분리와 `when` 조합으로 실무 시나리오는 대부분 표현되고,
문법이 복잡해지면 미리보기로 결과를 예측하기 어려워진다.
실제로 표현 안 되는 사례가 나오면 그때 추가한다.

## 8. 안전장치

### 8.1 격리 폴더 (휴지통 대신)

Windows 휴지통에 보낸 파일은 프로그램이 자동으로 되돌릴 수 없다.
`organize undo` 가 반쪽이 되므로, 실행 단위 격리 폴더를 쓴다.

**작업 루트**는 `roots` 의 각 항목을 해석한 경로다 (§7.1). 모든 step 의 target 이
구조적으로 그 root 하위이므로 위치가 자동으로 확정된다.
`.organize/` 는 각 작업 루트 바로 아래에 만든다.

`roots` 가 여러 개면 **root 마다 별도의 run 이 된다.** 로그와 격리 폴더도 root 마다 따로다.
한 root 가 실패해도 나머지는 계속한다. `organize undo` 는 root 를 지정하지 않으면
가장 최근 run 하나만 되돌린다.

프로파일의 `to` 가 `@archive/...` 처럼 root 밖을 가리켜 파일이 루트 밖으로 나간 경우에도,
로그에 원래 경로와 최종 경로가 모두 남으므로 되돌리기는 정상 동작한다.

```
<작업루트>/.organize/
    runs/
        20260819-143210.json        실행 로그
    trash/
        20260819-143210/            그 실행에서 치운 파일
            가이드 (1).pdf
            _manifest.json          원래 경로 기록
```

- 같은 드라이브 안 이동이라 즉시 끝난다 (복사가 아니다).
- `organize undo` 로 100% 원위치 복구된다.
- `organize trash --empty` 로 확인 후 진짜 삭제한다.
- 이 방식 덕분에 **외부 의존성이 0개가 된다** (`send2trash` 불필요).

### 8.2 그 외

| 장치 | 내용 |
|---|---|
| 기본이 미리보기 | `--apply` 를 명시하지 않으면 어떤 파일도 건드리지 않는다 |
| 실행 로그 | 실행마다 `runs/<id>.json` 에 전 항목 기록 |
| 되돌리기 | `organize undo` 가 로그를 역순 재생. 인자 없으면 가장 최근 실행 |
| 이름 충돌 | `이름_(1).확장자` 로 번호 부여 (기존 `result.py` 방식 계승) |
| 자기 폴더 보호 | `.organize/` 와 route 결과 폴더는 스캔 대상에서 제외 |
| 부분 실패 | 한 Action 이 실패해도 중단하지 않고 계속 진행. 실패 목록을 로그와 요약에 남긴다. 이미 성공한 것은 로그에 있으므로 undo 가능하다 |
| **온라인 전용 파일 제외** | OneDrive 등 클라우드에만 있고 디스크에 없는 파일은 스캔에서 걸러낸다. 열면 자동 다운로드가 시작되므로 **읽지도 않는다.** Windows 파일 속성 `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`(0x400000) / `OFFLINE`(0x1000) 로 판정하며 `ctypes` 로 읽는다 |
| **작업 중 파일 제외** | `.crdownload` `.part` `.tmp` `.partial` `.download` 확장자 + **최근 1분 내 수정된 파일**. 다운로드 중인 파일을 옮기면 다운로드가 깨진다 |
| **실행 직전 재검증** | 미리보기 때 기록한 크기·수정시각과 실행 시점을 대조한다. 다르면 그 항목만 건너뛰고 이유를 로그에 남긴다. 미리보기와 실행 사이에 사람이 파일을 건드렸을 수 있다 |
| 크로스 드라이브 | 원본과 대상 드라이브가 다르면 `copy2` 후 원본 삭제 (기존 로직 계승). 복사 검증 후 삭제한다 |

### 8.3 undo 의 한계

`extract` Action 은 되돌릴 때 압축을 푼 파일들을 격리 폴더로 옮긴다.
원본 zip 을 삭제했다면 그것도 격리 폴더에서 복구한다.
`trash --empty` 를 실행한 뒤에는 그 실행을 되돌릴 수 없다. UI에서 경고한다.

## 9. CLI

```
organize list                          레시피·프로파일 목록

organize run <recipe> --apply          실행
organize undo [run-id]                 되돌리기 (기본: 가장 최근)
organize trash --list                  격리된 파일 목록
organize trash --empty [run-id]        격리 폴더 비우기 (진짜 삭제)
organize gui                           GUI 실행
organize doctor                        환경 점검 (새 PC 에서 가장 먼저 실행)

organize schedule --daily 03:00        Windows 작업 스케줄러에 등록
organize schedule --list / --remove    예약 확인 / 해제

organize pin <파일 또는 패턴>            항상 제자리에 두기 (영구 제외)
organize pin --list / --remove

organize suggest                       99_Unsorted 에 쌓인 확장자 통계 → 규칙 추가 제안

organize do <블록> [옵션]               레시피 없이 블록 하나를 즉석 실행
```

```
organize do by_date --root @desktop --only "*.md" --dest "@documents/메모"
organize do dedup   --root @downloads
organize do route   --root @desktop --profile desktop
```

`do` 도 미리보기가 기본이며 `--apply` 를 붙여야 실행된다.

모든 실행 명령은 `--root <별칭 또는 경로>` 로 레시피의 `root` 를 덮어쓸 수 있다.
step 의 target 은 모두 상대 경로이므로 자동으로 새 루트 기준이 된다.

```
organize preview downloads --root @desktop      같은 레시피를 바탕화면에 적용
```

추가 명령:

```
organize paths                         현재 PC 에서 해석된 별칭 목록 출력
organize paths --set archive=F:/day    사용자 별칭 추가 (GUI 설정 화면과 동일)
```

### 9.1 `organize doctor`

새 PC 에 앉았을 때 무엇이 부족한지 한 번에 알려준다. 부족한 것이 있어도 나머지는 계속 점검한다.

```
$ organize doctor

  Python          3.14.6            OK   (3.11 이상 필요)
  tkinter         8.6               OK
  Pillow          없음              선택  EXIF 촬영일을 못 읽습니다.
                                          파일명과 수정시각으로 대체합니다.
                                          쓰려면: pip install Pillow

  폴더 위치
    바탕화면      C:\Users\...\Desktop        파일   6
    다운로드      C:\Users\...\Downloads      파일 121
    문서          C:\Users\...\Documents      파일  43
    사진          C:\Users\...\Pictures       파일   1
    @archive      F:\day                      없음!

  레시피 2개 · 프로파일 1개

  @archive 를 쓰는 레시피가 1개 있습니다. 위치를 지정해 주세요:
      organize paths --set archive=<경로>
      또는 설정 화면에서 지정
```

경로마다 **파일 개수를 함께 출력**한다. 경로 문자열만으로는 사용자가 맞는지 판단할 수 없다
(§3.4 OneDrive 문제).

### 9.2 출력 규칙

모든 명령은 **결과 뒤에 다음에 칠 명령어를 그대로 출력한다.**
사용자가 옵션을 다시 찾아보게 하지 않는다.

```
$ organize preview downloads

  [1/4] unzip     처리할 zip 없음
  [2/4] dedup     중복 3건
  [3/4] route     이동 118건
  [4/4] by_date   이동 105건

  총계  이동 223 · 격리 3 · 건너뜀 0

  실제로 실행하려면:
      organize run downloads --apply

  전체 목록을 보려면:
      organize preview downloads --verbose
```

```
$ organize run downloads --apply

  완료. 이동 223 · 격리 3 · 실패 0
  로그: .organize/runs/20260819-143210.json

  되돌리려면:
      organize undo

  격리된 3개 파일을 완전히 삭제하려면:
      organize trash --empty 20260819-143210
```

### 9.3 예약 실행

`organize schedule --daily 03:00` 은 Windows 작업 스케줄러(`schtasks`)에 등록한다.
자는 동안 돌므로 작업 중인 파일과 부딪힐 일이 거의 없다.

예약 실행은 **`--apply` 가 이미 켜진 상태로 돈다.** 사람이 확인할 수 없기 때문에
안전장치가 더 중요하다 — 실행 로그는 그대로 남고 `organize undo` 로 되돌릴 수 있다.
실행 결과 요약은 알림으로 띄운다.

예약을 걸어도 **수동 실행은 그대로 쓸 수 있다.** 둘은 같은 엔진을 쓴다.

### 9.4 고정(pin)

"이 파일은 항상 제자리" 를 기억한다. 바탕화면에 일부러 꺼내 둔 파일이
매번 끌려가는 것을 막는다.

```
organize pin "작업중.xlsx"
organize pin "*.lnk"
```

`config.local.json` 에 저장되며, 어떤 프로파일을 쓰든 적용된다.
미리보기의 "손대지 않음" 에 이유가 표시된다.

### 9.5 규칙 제안

`99_Unsorted` 에 쌓인 파일의 확장자를 세어 규칙 추가를 제안한다.
**AI 가 아니라 단순 집계**이므로 같은 폴더면 항상 같은 제안이 나온다.

```
$ organize suggest

  99_Unsorted 에 쌓인 확장자
    .hwpx   12개     이 확장자를 어디로 보낼까요?
    .apk     3개
    .torrent 2개

  규칙을 추가하려면:
      organize suggest --add .hwpx=01_Docs
```

```
| [v] 2  중복 제거     남길 파일: 짧은 경로 우선       |
| [v] 3  종류별 분류   설정: [ 바탕화면·다운로드  v ] |
| [ ] 4  연도별 분류   대상: 02_Media                 |
|                                     [^][v] 순서변경 |
+----------------------------------------------------+
|        [ 미리보기 ]      [ 실행 ]      [ 되돌리기 ] |
+- 미리보기 결과  (이동 223 · 격리 3 · 건너뜀 0) -----+
| 이동   screenshot_01.png -> 02_Media/   확장자 .png |
| 이동   setup.exe         -> 04_Apps/    확장자 .exe |
| 격리   가이드 (1).pdf     -> 격리폴더    중복        |
+----------------------------------------------------+
```

`대상` 은 경로 입력창이 아니라 **별칭 드롭다운**이다 (`다운로드`, `바탕화면`, `백업드라이브`...).
일반 사용자가 경로를 직접 칠 일이 없다. 목록에 없으면 `설정` 에서 추가한다.

**경로 옆 상태 표시가 이식성의 핵심이다.** 다른 PC 로 옮기면 없는 경로가 빨갛게 뜨므로,
사용자는 그것만 다시 지정하면 된다. 무엇을 고쳐야 하는지 찾아다닐 필요가 없다.

폴더 이름 편집 결과는 `config.local.json` 의 `folder_names` 에 저장된다 (§6.6).
확장자 목록과 상세 조건은 읽기 전용으로 보여주기만 한다.

### 10.4 구현 시 주의

- **스캔·실행은 별도 스레드에서 돈다.** 메인 스레드에서 돌리면 창이 얼어붙는다.
  진행 상황은 `queue.Queue` 로 전달하고 `after()` 로 폴링한다.
- 미리보기 목록이 5,000줄을 넘으면 `ttk.Treeview` 가 느려진다.
  상단 요약을 항상 보여주고, 상세 목록은 기본 접힘 + 필요 시 펼침으로 둔다.
- `[실행]` 버튼은 미리보기를 한 번 돌린 뒤에만 활성화한다.
- **오류 메시지는 사람 말로 쓴다.** 예외를 그대로 노출하지 않는다.

```
나쁨:  PermissionError: [WinError 5] Access is denied: 'F:\\day\\a.jpg'
좋음:  'F:\day\a.jpg' 를 옮길 수 없습니다.
       다른 프로그램이 이 파일을 열고 있는지 확인해 주세요.
       나머지 파일은 정상적으로 처리했습니다. (성공 220 / 실패 1)
```

### 10.6 범위 밖

레트로(게임보이) 외형은 1차 범위 밖이다. 기능이 검증된 뒤 별도 작업으로 다룬다.
tkinter 로는 둥근 모서리·그림자·회전이 안 되므로, 그때 가서 기술 선택을 다시 검토한다.

## 12. 의존성

| 대상 | 필요도 | 용도 |
|---|---|---|
| 표준 라이브러리만 | — | `tomllib`, `json`, `hashlib`, `zipfile`, `tkinter`, `ctypes` 전부 내장 |
| `Pillow` | **선택** | EXIF 촬영일. 없으면 파일명·mtime 으로 자동 폴백하고 경고만 출력 |
| `PyInstaller` | 빌드 전용 | exe 포장. 실행에는 필요 없다 (구현 마지막 단계) |

**필수 외부 의존성은 없다.** Python 3.11 이상이면 추가 설치 없이 바로 돈다 (§3.2).

## 13. 테스트 전략

TDD로 진행한다. 파일을 옮기고 지우는 도구이므로 테스트 없이 짜면 안 된다.

| 계층 | 방법 |
|---|---|
| 순수 함수 | `dates.py`, `hashing.py`, `profiles.py` 의 규칙 매칭 — 파일 없이 단위 테스트 |
| 블록 | `tmp_path` 픽스처에 가짜 폴더를 만들고 Plan 을 검증. **파일이 안 움직였는지도 확인** |
| 러너 | Plan → apply → undo 왕복 후 폴더 상태가 원래와 동일한지 확인 |
| 별칭 | `@downloads` 해석을 모킹해 레시피가 PC 무관하게 도는지 확인. 미정의 별칭에서 명확히 실패하는지도 |
| `when` 필터 | 프로파일 규칙과 같은 매칭 코드를 쓰므로 조건 테스트를 공유 |
| 설정 | `config.local.json` 읽기/쓰기 왕복, 폴더 이름 오버라이드가 프로파일 기본값을 덮는지 |
| 회귀 | `screenshot_1920x1080.png` 가 1920년으로 가지 않는지 등 기존 버그를 테스트로 고정 |

### 13.1 어느 PC 에서도 돌아야 한다

**테스트는 특정 PC 의 특정 폴더에 의존하지 않는다.** 개발 PC 가 바뀌어도 그대로 통과해야 한다.

- 모든 테스트는 `tmp_path` 에 필요한 파일 구조를 **직접 만들어서** 검증한다.
- 별칭 해석은 모킹한다. 실제 `@downloads` 가 어디를 가리키든 테스트 결과가 같아야 한다.
- 사용자의 실제 폴더를 읽거나 쓰는 테스트는 만들지 않는다.

테스트는 WSL 이든 Windows 든 `pytest` 한 번으로 돈다.

### 13.2 실사용 검증

기능이 붙을 때마다 실제 폴더에 `preview` 를 돌려 눈으로 확인한다.
**대상은 그때 그 PC 의 `@downloads` 다.** 특정 경로나 파일 개수를 고정하지 않는다.

`--apply` 로 넘어가기 전에 `preview` 결과를 반드시 사람이 본다.

참고로 2026-08-19 관측 시점의 대상 폴더는 121개 항목(png 105, exe 5, md 3, msix 2, html 2,
그 외 폴더 몇 개)이었다. 이는 검증 기준이 아니라 당시 기록이다.

## 14. 1차 범위 밖 (YAGNI)

의도적으로 넣지 않는다.

- 폴더 이름 변경 / 번호 접두사 붙이기
- Johnny.Decimal 프로파일
- 게임보이 레트로 UI
- 실행 이력 여러 개를 골라 되돌리기 (가장 최근 하나만)
- if/else 중첩·서브 파이프라인·반복문 같은 분기 트리 (§7.5)
- 스케줄 자동 실행
- 파일 내용 기반 분류 (OCR, 텍스트 추출 등)
- 상시 감시(watch) 모드 — 예약 실행으로 충분하고, 다운로드 중 파일과 부딪힐 위험이 크다
- 중복 파일을 삭제 대신 하드링크로 바꾸기
- 프로파일의 **상세 규칙**(확장자 추가/삭제, 조건 편집) GUI 편집 — 폴더 이름만 편집 가능(§6.6)

### 14.1 범위 안이지만 마지막에 하는 것

- **exe 포장 (PyInstaller).** 기능을 완성하고 실제로 써본 뒤 마지막 단계에서 만든다.
  구현 중에는 `python -m organize` 로 돌려야 고치는 속도가 빠르다.

## 15. 결정 기록

| 결정 | 이유 |
|---|---|
| 체인 실행 + 레시피 저장 | 여러 자동화를 골라 조합해 쓰는 것이 원래 목적 |
| `route` 하나로 종류별·번호별 분류 통합 | 둘 다 "파일 → 목적지 폴더명" 이라 같은 엔진. 프로파일만 교체 |
| 폴더명 `01_Docs` + `99_Unsorted` | 짧은 영문으로 폭 일정, CLI 이스케이프 불필요, 미분류가 항상 맨 아래 |
| Plan / Apply 분리 | 미리보기와 실행 결과의 일치를 구조적으로 보장 |
| 격리 폴더 (Windows 휴지통 아님) | 휴지통은 프로그램이 자동 복구할 수 없어 undo 가 성립하지 않음. 덤으로 의존성 0 |
| Windows 네이티브 실행 | `/mnt/c` 경유 해시 계산이 수십 배 느림 |
| tkinter | Windows Python 에 이미 있고 동작 확인 완료. 추가 설치 0 |
| TOML 프로파일 / JSON 레시피 | 프로파일은 손으로 쓰므로 주석 가능한 TOML, 레시피는 GUI가 쓰므로 JSON. 둘 다 표준 라이브러리 |
| AI 판정 없음 | 미리보기와 실행 결과가 반드시 같아야 함 |
| 경로 별칭 + `config.local.json` | 레시피를 PC 간 이식 가능하게. 이 PC 에 `Desktop` 과 `OneDrive\바탕 화면` 이 동시에 존재해 하드코딩이 실제로 위험함 |
| 사용자 폴더는 OS 에 질의 | OneDrive 리디렉션 때문. `SHGetKnownFolderPath` 는 `ctypes` 로 호출하므로 의존성 증가 없음 |
| 레시피 `root` + 상대 target | `--root` 하나로 다른 폴더에 재사용. 격리 폴더 위치도 구조적으로 확정됨 |
| 분기는 폴더 + `when` 만 | if/else 트리를 넣으면 미리보기로 결과를 예측하기 어려워짐 |
| `when` 문법 = 프로파일 규칙 문법 | 매칭 코드 재사용, 사용자가 새로 배울 것 없음 |
| 타인 배포를 전제 | 설정 파일을 손으로 고치게 하지 않는다. 오류 메시지도 사람 말로 |
| 읽기만 TOML / 쓰기도 하면 JSON | `tomllib` 은 읽기 전용이라 표준 라이브러리로 TOML 을 쓸 수 없다. 이 규칙으로 의존성 0 유지 |
| 폴더 이름은 오버라이드로 저장 | 원본 프로파일을 안 건드려서 도구를 업데이트해도 사용자 설정이 살아남음 |
| 첫 실행 화면에 파일 개수 표시 | 경로 문자열만으로는 OneDrive 리디렉션 오류를 사용자가 알아채지 못함 |
| 규칙 편집은 폴더 이름까지만 | 일반 사용자가 실제로 원하는 커스터마이즈의 대부분. 조건 편집기는 부피 대비 효용이 낮음 |
| exe 는 마지막 단계 | 구현 중에는 `.py` 로 돌려야 수정 속도가 빠름 |
| 개발 PC 를 전제하지 않음 | 현재 PC 를 2026-08-31 이후 쓰지 않는다. `legacy/` 스크립트가 이전 PC 경로로 죽은 것이 실제 사례 |
| 사양은 "Python 3.11+" 뿐 | 관측된 3.14.6 은 사실이지 요구사항이 아니다. `tomllib` 이 하한선을 정한다 |
| `organize doctor` 추가 | 새 PC 에서 무엇이 부족한지 사람이 찾아다니지 않게 |
| 테스트는 `tmp_path` 전용 | 개발 PC 가 바뀌어도 그대로 통과해야 한다 |
| 내장 별칭을 표준 폴더 전체로 | Windows 가 6개 폴더를 모든 PC 에 보장한다. 설정 0 으로 시작 가능 |
| `config.default.json` + `config.local.json` 2단 | 새 PC 에서 설정 없이 동작. 기본값은 전부 표준 폴더 아래 |
| 별칭에 대체 경로 목록 | 외장하드 유무·PC 변경에도 레시피가 죽지 않음. 설정이 유동적인 것이 이 도구의 장점 |
| 기본 프로파일은 "한 폴더에 모으기" | 2차 세분화를 하려면 먼저 한 곳에 모여야 한다. 표준 폴더로 흩뿌리면 기존 파일과 섞여 체인이 끊긴다 |
| 모든 블록에 `target`/`dest`/`when` 공통 | "어디서 찾아 어디로 보낼지"를 블록마다 다르게 배우지 않게 |
| 블록 1개짜리 레시피 = 예전 스크립트 | 체인은 선택지이지 강제가 아니다 |
| `has_exif_camera` 로 스크린샷 판별 | 파일명에 단서가 없어도 정확. 관측 사례에서 유튜브 캡처 105개가 이름만으로는 구분 불가였다 |
| `group_by`(묶음)는 2차로 | 실제로 써본 뒤 필요성을 확인하고 붙인다 |
| **로컬 파일만 다룬다** | 온라인 전용 파일을 읽으면 클라우드 다운로드가 시작된다. 관측 PC 의 `OneDrive\바탕 화면` 3개가 전부 온라인 전용이었다 |
| **폴더는 기본적으로 안 건드린다** | 폴더를 옮기면 바로가기·프로젝트 설정·터미널 경로가 깨진다. 옮기는 건 사용자가 명시적으로 켤 때만 |
| 대상은 `roots` 배열 | 사용자가 목록을 채운다. "하위 폴더를 어디까지 파고들까" 라는 판단 자체가 사라진다 |
| dedup 은 읽는 범위 ≠ 치우는 범위 | 하위 폴더를 참고만 하고 건드리지 않으면서도 중복 제거가 쓸모 있다 |
| 중복 폴더 방지 3단계 | 폴더가 늘어나면 정리가 아니라 더 어려워진다. 관측 PC 의 PicPick 에 `6월`·`6월9일` 이 이미 있었다 |
| 예약 실행만, 상시 감시는 안 함 | 자는 동안 도는 편이 다운로드 중인 파일과 부딪힐 위험이 적다 |
| 안전장치 3종은 협의 없이 포함 | 온라인 파일·작업 중 파일·실행 직전 재검증. 없으면 파일이 깨진다 |
