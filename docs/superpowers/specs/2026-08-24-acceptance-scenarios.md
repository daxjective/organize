# 실사용 검증 시나리오

**목적** — 실제 폴더에서 정말 원하는 대로 도는지 확인한다. 테스트 274개가
통과하는 것과 "내 다운로드 폴더에서 쓸 만한가" 는 다른 얘기다.

**언제** — 두 번 한다.
1. **8월 31일 전**, 지금 이 PC 에서 (실제 파일이 여기 있다)
2. **새 PC 에서**, 그 PC 로 옮긴 뒤 (경로가 자동으로 잡히는지가 핵심)

**전제** — `Task 18` 이 끝나 CLI 가 붙은 뒤에 한다. 그 전에는 파이썬에서 직접
불러야 하고, 그러면 "쓸 만한가" 를 판단할 수 없다.

---

## 0. 규칙 — 이 순서를 지킨다

1. **`--apply` 없이 먼저 본다.** 미리보기가 기본이다.
2. 미리보기에서 **한 줄이라도 이상하면 실행하지 않는다.** 그게 버그다.
3. 실행한 뒤 **`undo` 를 반드시 한 번 해 본다.** 되돌리기가 되는지 확인하기 전에는
   다음 폴더로 넘어가지 않는다.
4. 매 단계에서 **본 것과 실제 결과가 같은지** 확인한다. 이 도구의 핵심 약속이다.

**절대 하지 말 것** — 검증 전에 사진 폴더 원본에 `--apply` 를 쓰지 않는다.
먼저 복사본을 만들어 그쪽에서 돌린다.

```
# 안전한 검증 방법 (윈도우 PowerShell)
Copy-Item -Recurse "$env:USERPROFILE\Pictures" "$env:USERPROFILE\Pictures_검증용"
```

## 1. 다운로드 폴더

**무엇이 들어 있나** — 설치 파일, 알집, 문서, 사진이 뒤섞여 있고 같은 걸 여러 번
받은 중복이 많다. 이 도구가 가장 값어치를 내는 곳이다.

**레시피**

| 순서 | 작업 | 대상 | 왜 이 순서인가 |
|---|---|---|---|
| 1 | `unzip` | 전체 | 알집 안을 먼저 꺼내야 그 안의 것도 분류된다 |
| 2 | `dedup` | 전체 | **분류보다 먼저.** 흩어지고 나면 중복을 못 찾는다 |
| 3 | `route` (`desktop`) | 전체 | 종류별로 나눈다 |
| 4 | `by_date` | `02_Media` | 사진·영상만 연도별로 |

```
organize preview 다운로드
organize run 다운로드 --apply
organize undo
```

**확인할 것**

- [ ] 같은 파일을 두 번 받은 것들이 격리 폴더로 갔는가 (`(1)`, `사본` 이 붙은 것들)
- [ ] **이름이 전혀 다른데 내용이 같은 파일**도 잡았는가 — 이름으로 판정하지 않는다
- [ ] 반대로 `IMG_1234.jpg` 처럼 숫자만 붙은 **다른** 파일을 중복으로 오판하지 않았는가
- [ ] 설치 파일(`.exe`, `.msi`)이 `04_Apps` 로 갔는가
- [ ] 알집이 풀린 뒤 알집 자체는 `05_Archives` 로 갔는가
- [ ] 알집 안 한글 파일명이 깨지지 않았는가 (`ÆÇ¡` 같은 게 안 보이는가)
- [ ] **미리보기에 보인 경로와 실제 경로가 같은가**
- [ ] `undo` 후 다운로드 폴더가 원래대로 돌아왔는가
- [ ] `undo` 후 **압축에서 나온 파일이 격리 폴더로 갔는가** (바탕화면에 남지 않았는가)
- [ ] 한 번 더 돌려도 폴더가 겹겹이 쌓이지 않는가 (`01_Docs/01_Docs`)

## 2. 문서\PicPick 폴더 — 컴퓨터 화면 캡처

**무엇이 들어 있나** — PicPick 으로 찍은 화면 캡처들. 브레인스토밍 때 실측한 결과
**중복 21쌍**이 있었고, **그 중복들은 이름이 전혀 달랐다.** 반대로 `(2)`, `(3)` 이
붙은 파일들은 서로 다른 이미지였다. 이름으로 판정하면 정확히 거꾸로 간다.

**레시피** — 캡처는 종류가 하나뿐이라 분류가 필요 없다.

| 순서 | 작업 | 대상 | 비고 |
|---|---|---|---|
| 1 | `dedup` | 전체 | 이게 이 폴더의 핵심 |
| 2 | `by_date` | 전체 | 연도별. `{year}/{month}` 도 고려 |

```
organize preview 캡처정리
organize run 캡처정리 --apply
```

**확인할 것**

- [ ] 이름이 다른데 내용이 같은 21쌍을 실제로 잡았는가
- [ ] `(2)`, `(3)` 붙은 **다른** 이미지를 중복으로 오판하지 않았는가
- [ ] `6월/` 같은 **하위 폴더 안 파일은 안 움직였는가** — 읽기만 해야 한다
- [ ] 하위 폴더에 같은 내용이 있으면 **직속 파일이 치워졌는가** (반대가 아닌가)
- [ ] 연도가 파일명·수정시각 중 맞는 쪽에서 왔는가
- [ ] 날짜를 못 읽은 파일이 **1970 폴더로 가지 않았는가** — 그 자리에 남아야 한다

## 3. 사진 폴더 — 휴대폰 사진과 휴대폰 캡처가 섞여 있음

**무엇이 들어 있나** — 갤럭시로 찍은 사진과 휴대폰 화면 캡처. 파일명만으로는
구분이 안 된다(둘 다 `20260820_085659.jpg` 꼴).

**핋심 판정** — EXIF 에 카메라 정보(`Make`/`Model`)가 있으면 사진, 없으면 캡처다.
브레인스토밍 때 실측으로 확인했다. 갤럭시 사진은 `True`, 휴대폰 캡처·PicPick
캡처·유튜브 캡처 5장은 모두 `False`.

**레시피**

| 순서 | 작업 | 대상 | 설정 |
|---|---|---|---|
| 1 | `route` (`photos`) | 전체 | `사진` / `캡처` 로 갈라짐 |
| 2 | `by_date` | `사진` | 찍은 사진만 연도별로 |

```
organize preview 사진정리
organize run 사진정리 --apply
```

**확인할 것**

- [ ] 찍은 사진이 `사진/` 으로, 화면 캡처가 `캡처/` 로 갔는가
- [ ] **파일명에 `screenshot` 이 없는 캡처**도 제대로 갈렸는가
- [ ] 연도가 **EXIF 촬영일**에서 왔는가 (파일 수정시각이 아니라)
- [ ] `Pillow` 가 없는 PC 에서도 죽지 않고 파일명·수정시각으로 폴백하는가
- [ ] OneDrive 로 옮겨진 사진 폴더라면 — **온라인 전용 파일을 건드리지 않았는가**
      (받아오려 들면 안 된다)

**레시피** — 가장 단순하게. 바탕화면은 매일 보는 곳이라 변화가 예측 가능해야 한다.

| 순서 | 작업 | 대상 |
|---|---|---|
| 1 | `route` (`desktop`) | 전체 |

```
organize preview 바탕화면
```

**확인할 것**

## 6. 아직 확인 안 된 것 — 반드시 여기서 찔러볼 것

개발은 WSL(리눅스)에서 했다. **아래는 논증만 했고 실제 윈도우에서 확인하지 않았다.**
"확인했다" 고 말할 수 없는 항목들이다.

| 무엇 | 왜 리눅스에서 확인이 안 되는가 |
|---|---|
| 경로가 정리 대상 폴더 밖으로 나가는 것 막기 | `C:\`, `\\서버\공유` 형태 판정을 리눅스에서 못 돈다 |
| 드라이브를 넘는 이동 (`C:` → `D:`) | 운영체제가 주는 오류 번호가 윈도우에서 다를 수 있다. **다르면 드라이브 넘는 이동이 통째로 실패한다** |
| 경로 260자 제한 | 리눅스에 그 제한이 없다 |
| 대소문자 무시 (`A.txt` == `a.txt`) | 리눅스는 다른 파일로 본다 |
| 열려 있는 파일은 이동 불가 | 리눅스는 열려 있어도 옮겨진다 |
| 바로가기(`.lnk`) · junction | 리눅스에 없는 개념이다 |
| 강제 종료 후 남는 0바이트 파일 | `doctor` 가 찾아 알려주는지 확인 |

**드라이브 넘는 이동을 반드시 실제로 해 볼 것.** `C:` 의 파일을 `D:` 로 보내는
레시피를 한 번 돌린다. 여기서 막히면 백업 드라이브로 정리하는 시나리오가 통째로
안 된다.
